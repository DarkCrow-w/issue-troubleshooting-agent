# 复杂交易场景验证报告

## 验证范围

本轮依据日志截图中可见的结构特征，构造了 50 笔完全合成的交易。数据保留了 Splunk `result` 包装、Kubernetes/Envoy 元数据、`correlationId`、复合 `seqNo`、`contextId`、`x_request_id`、转义 JSON、Java 异常链和敏感请求头等结构，但没有复制真实业务值。

每个场景都经过真实的 `InvestigationService` 和 LangGraph 工作流，覆盖日志检索、标准化、请求响应配对、异常分析、调用图重建、失败定位、报告生成和 PostgreSQL 原始证据落库。确定性回归使用离线规则模式，避免模型输出波动掩盖解析和编排缺陷。

运行命令：

```bash
.venv/bin/pytest backend/tests/test_complex_scenarios.py -q
```

## 发现并修复的问题

### 1. 带原因短语的 HTTP 状态被漏判

原实现直接执行整数转换，`503 Service Unavailable` 会变成 `None`，最终报告漏掉 HTTP 失败。现在只从状态字段开头提取合法的三位状态码，并限制在 100–599。

### 2. `message` 和 `throwable` 中的 Java 异常未被分析

原实现只检查 `stacktrace`、`exception` 和 `_raw`。许多 Java JSON logger 把异常写入 `message` 或 `throwable`，导致异常类型和原因丢失。现在按信息完整度依次检查 `stacktrace`、`throwable`、`exception`、`message` 和 `_raw`。

### 3. direction 不同导致请求响应被拆分

原配对键包含 `direction`。同一调用的请求可能记录为 outbound，响应记录为 inbound，因此被错误拆成两个节点。现在使用服务、实例、调用 ID 和重试次数配对，方向只作为观察属性。

### 4. 测试数据和证据语义问题

首轮有一个 epoch 值落在查询窗外，已校准为目标时间；另一个测试曾错误要求 PostgreSQL 删除长请求体。当前设计明确区分两类数据：模型输入可以清洗压缩，证据库存放完整原始日志，便于审计和回看。

## 最终结果

- 复杂场景：50/50 通过。
- 后端完整回归：53/53 通过。
- Ruff 静态检查：通过。
- Ruff 格式检查：通过。
- 原始值保留：检查 PostgreSQL evidence payload 中的结构化字段和字符串内容均未被替换。
- 清洗效果：检查 `after_chars < before_chars`，并验证关键交易字段仍可用于分析。
- 大日志覆盖：4.5 MB 请求体经过完整 Agent 流程；独立回归验证头部、尾部以及分布在中后段的 Java 异常和业务错误码窗口均被保留。

## 当前仍需在公司环境验证的边界

1. 本地 ReplaySource 可以复现 Splunk 结果结构，但无法验证公司 Splunk 的索引权限、字段抽取规则、分页、限流和网络超时。
2. 确定性测试覆盖 Agent 编排和规则事实；当前本机未配置 LLM API key，因此没有把外部模型输出质量计入通过条件。模型判断仍应通过少量公司样本做联调。
3. “最早观测失败”依赖日志时间。跨主机明显时钟漂移时，报告只能提示风险，不能自动证明根因顺序。
4. 没有 call/span ID 时，Agent 会保守地保留孤立节点，不按时间强行配对。若公司日志有稳定的自定义调用字段，应加入配置或定制 Skill。
5. 新出现的业务成功码、服务别名和关联字段需要在 `config/settings.yaml` 中维护，否则可能产生可解释的误报或证据缺口。
